## 二十三、display logbuffer 仍报"几天前的 Error 日志" —— 根因=runserver 没重启 + 解析依赖 locale 隐患
- 用户报：fw001 巡检 `display logbuffer` 仍显示 `存在 1 条 Error 及以上级别日志: %Jul 17 16:03:35:293 2026 ...`，但今天已 7/23，属历史日志。
- 排查：磁盘上 `check_logbuffer`+`_parse_log_time` 时间窗口逻辑其实**是对的**（默认 window_days=2，7/17 < 7/21 截止日应被跳过）；但 DB 里 `display logbuffer` 的 `checker_config={'func':'check_logbuffer'}` 没显式带 window_days，且**运行中的 runserver 仍是旧代码（无时间窗口过滤的版本），上一次加窗口的改动只在磁盘、从未重启过** → 内存里跑的是旧逻辑，历史日志照样报。
- 另发现隐患：`_parse_log_time` 用 Python `%b` 英文月名解析，一旦运行环境 locale 设成中文，月份解析失败返回 None → 近期真实错误会被 `if ts is None: continue` 静默跳过（漏报）。
- 修复：
  1. `app02/custom_checks.py`：`_parse_log_time` 改为**硬编码月份表(_MONTH_MAP)解析、不再依赖 locale**，ISO 风格路径保留；彻底消除 locale 导致的漏报/误判风险。
  2. DB 直改（本机库）：`display logbuffer` 的 `checker_config` 显式写入 `{'func':'check_logbuffer','window_days':2}`（自文档化，不依赖默认值）。
- 验证：locale 无关单测 → 7/17 日志 `ts<cutoff` 判定为历史跳过、7/23 日志在窗口内；`manage.py check` 0 issues。
- ⚠️ **关键提醒：用户必须重启 runserver 才能让新 `check_logbuffer` 生效**（老问题：runserver 热重载偶尔漏加载 custom_checks/parsers）。重启后重跑该设备巡检，7/17 这条就不会再出现了；若 7/21–7/23 仍有真实 Error 日志则正常报出（window_days=2 即"最近两天"设计如此，如需更宽可在网页/DB 改 window_days）。
